## 4. Customer-Facing UX Gaps

### Branding and purpose

- Home page reads like an internal test harness (“test suite” and “Test Scenarios”), not a customer-facing landing.
- Routes are demo-centric and lack product framing or user journey guidance.

Evidence: src/routes/+page.svelte:L10-L34

### Debug tooling exposure

- Debug panel is mounted globally regardless of environment, which is risky for production UX and data exposure.
- Debug output includes request metadata and raw data views, which can leak sensitive details if shipped.

Evidence: src/routes/+layout.svelte:L10-L13, src/lib/components/DebugData.svelte:L1-L105

### Content tone and clarity

- Many pages use dev-centric labels (“Matrix”, “SSR ON/OFF”, “Negotiation”).
- Error and status pages provide limited guidance for end users.

Evidence: src/routes/matrix/ssr-on/+page.svelte:L1-L6, src/routes/matrix/ssr-off/+page.svelte:L1-L7, src/routes/status/+page.svelte:L1-L7, src/routes/negotiate/+page.svelte:L1-L6

### Accessibility and visual consistency

- Most pages use inline styles and no shared design system.
- Minimal heading hierarchy and skip navigation; no global nav.

Evidence: src/routes/+page.svelte:L38-L63, src/routes/form-basic/+page.svelte:L1-L49, src/routes/parent-child/+page.svelte:L1-L58

## 5. Open-Source Developer Ergonomics Gaps

### Discoverability and examples

- Routes are examples but not clearly documented as such in the UI.
- No in-app “How to run locally” link or “Read the docs” CTA.

Evidence: src/routes/+page.svelte:L14-L34

### Debug tooling UX

- Debug panel is powerful but lacks a documented “production off” mode and a configuration switch.
- Some debug behaviors depend on `APP_ENV` or `dev` but the mounting is unconditional.

Evidence: src/routes/+layout.svelte:L10-L13, src/lib/components/DebugData.svelte:L31-L61, src/routes/+layout.server.php:L18-L19

### PHP dev proxying clarity

- `getPhpData` assumes localhost:8080 and hardcodes the bridge URL, which is okay for tests but not configurable.
- This makes onboarding harder for contributors using a different PHP port or base path.

Evidence: src/lib/server/php-dev.ts:L18-L33

### Adapter variants and naming

- Multiple adapters exist (apache, dev, vite-dev, core) but there is no decision tree or comparison table.
- Apache adapter generates its own bootstrap and .htaccess; the main adapter has different output semantics.

Evidence: adapter/src/apache-adapter.ts:L1-L246, adapter/src/dev-adapter.ts:L1-L62, adapter/src/vite-dev-adapter.ts:L1-L114, adapter/src/index.ts:L12-L44

## 6. Security & Data Exposure Review

- Debug panel displays raw request and app data; global mounting increases risk if shipped accidentally.
- File uploads store artifacts in a public build folder, which is acceptable for demo but risky for production.
- Cookie sample lacks `secure` and `samesite` defaults, which may mislead production use.

Evidence: src/lib/components/DebugData.svelte:L1-L105, src/routes/form-multipart/+page.server.php:L32-L44, src/routes/api/cookie/+server.php:L7-L11

## 7. Recommendations (Prioritized)

### High Priority

1. **Add an explicit “demo vs production” switch** for DebugData and dev-only UI.
   - Gate DebugData mount in layout with `dev` or `APP_ENV` and document the env.
   - Add a visual banner for “Demo Mode” to avoid confusion.

2. **Replace the home page test menu with a “product” landing and a demo index**.
   - Split into “Docs / Examples” and “Product / Features” sections.
   - Provide clear links to setup guides and OSS contribution docs.

3. **Document a portable PHP dev bridge**.
   - Move host/port/base into env-configurable values.
   - Add a short section in docs for dev proxy overrides.

### Medium Priority

4. **Add a lightweight UI shell** (header/footer, global nav, typography).
   - Reduces the “test harness” feel without changing demo routes.

5. **Improve route labels and copy** for non-technical audiences.
   - “Matrix: SSR On” → “Server Rendering Enabled”
   - “Negotiation” → “Content Negotiation (HTML vs JSON)”

6. **Strengthen example security disclaimers**.
   - Call out upload directory behavior.
   - Add `secure` + `samesite` guidance for cookies.

### Low Priority

7. **Add an “API Playground” page** to explain endpoints and sample curl commands.
8. **Add i18n readiness** (language placeholder and locale selection).
9. **Add “getting started” tasks** in UI: “Install PHP”, “Run build”, “Start server”.

## 8. Suggested Doc Additions

- “Demo Mode vs Production Mode” section in README or ADAPTER_INSTRUCTIONS.
- “Adapter Selection Guide” with a decision table for core vs apache vs dev adapters.
- “Local Dev Checklist” with PHP port/base configuration examples.

Evidence: docs/ADAPTER_INSTRUCTIONS.md:L1-L316, scripts/dev-php.mjs:L1-L95

## 9. Summary

The project is strong as a technical demo, but it needs clearer separation between **demo tooling** and **production UX**, plus a more welcoming onboarding experience for open-source contributors. The most impactful improvements are (1) gating debug tools, (2) reframing the landing page and navigation to feel customer-facing, and (3) making dev proxy configuration obvious and flexible.
