# Execution Plan — 2026-01-20

## 1. Executive Summary

This execution plan captures the review outcomes for enabling PHP-backed route modules to behave like standard SvelteKit server modules. The goal is to keep prerender-first output while allowing `+page.server.php`, `+layout.server.php`, and `+server.php` as first-class alternatives to TS/JS server modules, aligned with SvelteKit routing conventions.

## 2. Scope of Review

- Routing and precedence for PHP server modules under `src/routes`.
- Build output shape in `php-static` and `node-ssr` modes.
- Runtime PHP glue for data loads, actions, endpoints, headers/cookies, and streaming.
- Compatibility with SvelteKit load semantics and navigation payloads.

## 3. Current Capabilities (Verified in Code)

- PHP server modules are discovered and compiled into `_protected` copies with generated `__data.php`, `__action.php`, and endpoint handlers in `php-static`.
- `__data.json` is rewritten to `__data.php` for navigation payloads and hydration data injection.
- `+server.php` endpoints are supported with method routing and param extraction.
- Route matching aligns with SvelteKit patterns (groups ignored, dynamic/rest/optional params).

## 4. Gaps and Risks

- `node-ssr` mode does not support PHP loads/actions; only PHP endpoints are copied.
- PHP RequestEvent parity is partial (missing `parent()`, `fetch`, `depends`, `locals`, cookie setters).
- Redirect/error semantics rely on header side effects and are brittle for navigation payloads.
- Non-enhanced actions return JSON instead of an HTML response, diverging from SvelteKit.
- No enforced precedence when both PHP and TS/JS server modules exist.
- Devalue compatibility is partial for non-JSON types.

## 5. Recommended Design for `.server.php`

### 5.1 Naming + Precedence Rules

- Allow: `+page.server.php`, `+layout.server.php`, `+server.php`.
- Reset only via `+page@.server.php` and `+layout@.server.php`.
- Build error on mixed PHP and TS/JS server modules at the same segment.

### 5.2 Runtime Contract

- `load($event)` returns JSON-serializable array data.
- `action_default` / `action_name` return ActionResult-like arrays or use `sk_fail`.
- Endpoints return `{ status, headers, body }` with JSON auto-encoding when body is array/object.

### 5.3 Prerender-First Behavior

- Keep `php-static` as primary mode for PHP-backed data.
- Preserve prerendered HTML; inject runtime data via `__data.php` on navigation/hydration.

## 6. Required Changes

- Build: enforce PHP/TS conflict checks; standardize reset filenames; emit PHP route manifest.
- Runtime: expand RequestEvent parity (cookies set/delete, `parent()`, `fetch` placeholder, `locals`).
- Actions: align non-enhanced behavior to redirect or HTML response when applicable.
- Redirect/error: add PHP helpers to model SvelteKit `redirect`/`error` flows robustly.
- Optional new mode: `node-ssr + php-data` where `__data.json` routes to PHP while HTML proxies to Node.

## 7. Execution Steps (Planned)

1. Add server-module conflict detection and reset naming normalization.
2. Expand PHP RequestEvent to closer SvelteKit parity and add redirect/error helpers.
3. Adjust action handling for non-enhanced form submissions.
4. Document precedence rules, PHP module contract, and mode limitations.

- Navigation payloads, redirects, actions, and endpoints match SvelteKit expectations.
- All checks and tests pass on PHP 7.4+ and PHP 8+.
